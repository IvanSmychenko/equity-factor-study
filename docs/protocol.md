# Протокол исследования: оценка вневыборочной полезности факторов

**Версия протокола:** 0.1

Документ описывает порядок сбора и подготовки данных, а также правила
построения итоговой месячной панели. Реализация соответствует требованиям
инвариантов, перечисленных ниже; любое нарушение считается дефектом.

## 1. Инварианты

1. **Отсутствие утечки информации.** Для наблюдения с целевым месяцем `t+1`
   используются только данные, доступные на конец месяца `t`. Для ключевой
   ставки берётся значение, действовавшее на последний торговый день месяца `t`.
2. **Разделение слоёв.** Сетевые вызовы допускаются исключительно в слое
   `clients` и в pipelines сбора. Построение панели и диагностика работают
   только с локальными файлами.
3. **Неизменность исходных данных.** Сохранённые ответы источников не
   перезаписываются и не редактируются. Повторный запуск сбора создаёт новый
   каталог выгрузки с собственным идентификатором.
4. **Детерминизм.** При фиксированном зерне генератора и одинаковых исходных
   данных два прогона дают идентичное содержимое итоговых файлов (кроме полей
   с меткой времени).
5. **Единая маска доступности.** Множество пригодных наблюдений определяется
   один раз и используется одинаково для всех моделей.
6. **Нормировка только на обучающих данных.** Параметры масштабирования
   вычисляются в пределах обучающего окна и применяются к проверочным
   наблюдениям без пересчёта.

## 2. Периоды и ключевые даты

Параметры периодов задаются в `configs/study.toml` (секция `[period]`) и
используются всеми этапами.

| Параметр | Значение (0.1) | Смысл |
|---|---|---|
| `download_start` | 2013-07-01 | Начало загрузки данных (за 6 мес. до наблюдения) |
| `observation_start` | 2014-01-01 | Начало периода наблюдения |
| `observation_end` | 2026-09-30 | Конец периода наблюдения |
| `development_target_end` | 2020-12-31 | Конец периода разработки |
| `evaluation_target_start` | 2021-01-01 | Начало периода оценки |

## 3. Окно обучения и дата первого прогноза

Длина окна обучения `W` (по умолчанию 48 месяцев) относится к числу
завершённых пар «признаки месяца `s` — доходность месяца `s+1`», в которых
доступен полный набор из пяти признаков.

Порядок вывода:

1. Пара сдвигается на месяц вперёд: последняя пара, доступная при прогнозе на
   месяц `t+1`, — это пара `s = t−1`.
2. Маска полного набора признаков сдвигает начало ряда. При данных с января
   2014 связывающим ограничением является моментум (требует цены
   четырёхмесячной давности), поэтому первая строка с полным набором — **май
   2014** (`s₀`).
3. Формула первого целевого месяца: `s₀ + W + 1`. При `s₀ = май 2014` и
   `W = 48` первый целевой месяц — **июнь 2018**.

### Контрольные даты (проверяются тестами)

| Величина | Значение (0.1) |
|---|---|
| Первая строка по маске (`s₀`) | май 2014 |
| Первый целевой месяц | июнь 2018 |
| Число прогнозов периода разработки | 31 |
| Число прогнозов периода оценки | 69 |
| Всего прогнозов | 100 |
| Первая дата пересмотра состава | июль 2019 |
| Последний оцениваемый целевой месяц | сентябрь 2026 |
| Число пар в окне первого прогноза | 48 |

Прогнозы считаются по **целевым месяцам**, а не по строкам панели. Строка
панели за сентябрь 2026 имеет пустую целевую переменную и не является
прогнозом. Число строк панели по бумаге с непрерывным покрытием равно числу
месяцев с января 2014 по сентябрь 2026 (153), тогда как число прогнозов — 100.

## 4. Дата первого пересмотра состава (модельный слой)

Относится к модельному слою и реализуется отдельным этапом. Датой первого
пересмотра считается первое июля 2019: первая ошибка доступна для целевого
месяца июня 2018, для пересмотра требуется двенадцать завершённых месяцев
прогнозов, а квартальная сетка допускает даты 1 апреля, 1 июля, 1 октября и
1 января. В апреле 2019 доступно лишь десять ошибок, в июле 2019 — двенадцать.

## 5. Конфигурация

Все параметры протокола, включая периоды, состав признаков и параметры
бутстрэпа, задаются в `configs/study.toml` и не зашиваются в код в виде
литералов. Модуль `equity_factor_study.config` загружает файл, проверяет типы,
диапазоны и взаимную согласованность значений и возвращает неизменяемый объект.
Неизвестные ключи приводят к ошибке.

### Зафиксированные решением значения (Б.4)

- **Допуск по концу месяца** — пять торговых дней: цена закрытия допустима,
  если отстоит от календарного конца месяца не более чем на пять торговых
  дней (`month_end.max_trading_days_from_month_end = 5`).
- **Разогрев правила отбора** — прогнозы целевых месяцев периода разработки
  используются исключительно для накопления ошибок и не входят в метрики
  оценки (`selection.warmup_from = "development"`).
- **Агрегация при отборе** — сначала по акциям внутри месяца, затем по
  месяцам (`aggregation = "securities_then_months"`), тот же порядок, что и
  для итоговых метрик.

## 6. Зерно генератора

`seed = 20140101` задаётся один раз на уровне всей работы. На этапах сбора и
построения панели зерно только валидируется, сохраняется в конфигурации и
переносится в манифест. Панель от зерна не зависит; отсутствие этой
зависимости проверяется на этапе 8.

## 8. Полная пагинация истории MOEX (этап 3)

Клиент MOEX собирает полную историю по инструменту за запрошенный интервал
вместо одной страницы. Правила:

* Размер страницы берётся из курсора ответа (`PAGESIZE`), а не задаётся
  константой.
* Итерация продолжается до пустой страницы либо до достижения общего числа
  записей из курсора (`TOTAL`).
* Позиция следующей страницы определяется по `INDEX` из курсора; при
  отсутствии курсора — по размеру текущей страницы.
* Защита от зацикливания: если очередная страница не продвигает позицию
  (возврат `INDEX` назад или неположительный размер), сбор прерывается
  с ошибкой `MOEXHistoryError`.
* После сбора проверяется отсутствие дублей по паре «инструмент — торговая
  дата» и полнота относительно `TOTAL` курсора.
* Каждая страница сохраняется отдельным файлом с собственными метаданными.

Сводка загрузки по инструменту (`HistoryDownload`) содержит число страниц,
число строк и интервал дат; сумма строк по страницам совпадает с итогом.

## 9. Клиент Банка России (этап 2)

Клиент `equity_factor_study.clients.cbr` запрашивает дневной ряд ключевой
ставки методом `KeyRateXML` веб-сервиса DailyInfo Банка России по протоколу
SOAP 1.1.

### Транспорт

* Адрес: `https://www.cbr.ru/DailyInfoWebServ/DailyInfo.asmx`.
* Запрос — `POST` с SOAP-конвертом (`text/xml; charset=utf-8`).
* Пространство имён: `http://web.cbr.ru/` без изменений.
* Параметр дат: `fromDate` и `ToDate` (регистр как в сервисе), значение —
  дата в формате ISO. Сроки меняются местами `fromDate`/`ToDate`.
* Заголовок `SOAPAction: http://web.cbr.ru/KeyRateXML`.

### Структура ответа (по фактическому ответу)

Ряд представлен элементами `KeyRate`/`KR`; поля строки ряда:

| Поле | Тип | Смысл |
|---|---|---|
| `DT` | dateTime | Дата последнего торгового дня (с временной зоной, дата берётся без времени) |
| `Rate` | строка | Значение ключевой ставки, процентов годовых |

Ответ разбирается безопасным парсером `defusedxml` без исполнения кода.
SOAP Fault преобразуется в `CBRFaultError` с текстом `faultstring`;
отклонение от ожидаемой структуры — в `CBRResponseError`. Пустой период
возвращает пустую таблицу без ошибки.

### Нормализация

`CBRClient.get_key_rate` возвращает `KeyRateDownload` с таблицей колонок
`date` (datetime.date) и `rate` (float, процентов годовых), строки
упорядочены по возрастанию дат. Единица измерения фиксируется в поле
`unit = "percent_per_annum"`. Исходный ответ и метаданные сохраняются через
`storage.save_response` (запрет перезаписи, контрольная сумма).

## 9.1. Справочники и историческая совокупность (этап 4)

Модуль `equity_factor_study.pipelines.catalog` загружает справочник режима
торгов (`iss/.../boards/{board}/securities.json`), пагинируя его, и
фильтрует обыкновенные акции.

### Тип бумаги

Конфигурация описывает тип бумаги семантической меткой (`security_type =
"common_share"`), тогда как MOEX использует числовые коды (`SECTYPE = "1"`).
Функция `resolve_security_type` приводит метку к коду источника; числовой код
оставляется без изменений, неизвестная метка отвергается ошибкой. Поэтому
фильтр применяется к правильному коду, и в продакшене выбор не сужается до
пустого множества.

### Построение выборки

`equity_factor_study.pipelines.universe` строит историческую совокупность:

* собирает оборот каждого кандидата за год `turnover_year` по дневным
  значениям `VALUE` полной истории;
* ранжирует кандидатов по обороту убывающе (нарушение равенства разрешается
  алфавитно по `secid` — детерминизм);
* отбирает `target_size` инструментов с наибольшим оборотом; при недостижении
  целевого числа допустимо меньшее число (`allow_fewer = true`);
* фиксирует каждого исключённого кандидата с причиной
  `not_selected_low_turnover`, значением оборота и рангом.

### Файл-замок и исключения

* **`configs/universe.lock.toml`** — состав выборки (`secids`), версия
  протокола, режим торгов и год отбора. Замок подлежит контролю версий; его
  изменение означает пересмотр состава и должно быть зафиксировано в журнале
  решений.
* **`configs/universe_exclusions.csv`** — перечень исключённых кандидатов с
  причиной, оборотом и рангом.

Оба артефакта размещаются рядом с файлом конфигурации, а не внутри
пер-прогонной выгрузки raw-данных. Наличие замка используется всеми
последующими этапами; повторный отбор при его наличии не выполняется.

## 9.2. Загрузка цен и ключевой ставки (этап 5)

Модули `equity_factor_study.pipelines.prices` и
`equity_factor_study.pipelines.key_rate` выполняют полную загрузку дневных
данных по выборке и нормализуют их в единые дневные таблицы.

### Дневные цены (`prices`)

`collect_prices` загружает полную историю по каждому инструменту из
`universe.lock.toml` за период `download_start..observation_end`, отбрасывает
строки не выбранного режима торгов и приводит данные к единым типам.

Нормализация (`normalize_history`):

* оставляет только строки с `BOARDID == selection_board`;
* приводит `TRADEDATE` к `date` (единый формат);
* приводит `CLOSE` и `VALUE` к `float`, обрабатывая разделитель-запятую;
* удаляет дубли по паре «инструмент — дата»;
* сортирует по `secid` и `trade_date`.

Таблица содержит колонки `secid`, `trade_date`, `close`, `value` и
сохраняется в `data/interim/daily_prices.csv`. Для каждого инструмента
формируется сводка (`InstrumentSummary`): число строк, интервал дат, число
пропущенных торговых дней и статус завершённости.

### Ряд ключевой ставки (`key-rate`)

`collect_key_rate` загружает дневной ряд ставки за период
`observation_start..observation_end` через `CBRClient` и нормализует его
(`normalize_key_rate`): колонки `date` (date) и `rate` (float), сортировка по
дате, удаление дублей дат. Результат — `data/interim/key_rate.csv`.

Сводка (`KeyRateSummary`) содержит число строк, интервал, число разрывов
покрытия (пропущенные будние дни внутри интервала) и статус завершённости.

Оба CLI-команды `prices` и `key-rate` принимают `--raw-dir` (выгрузка
источников с уникальным каталогом прогона) и `--interim-dir` (каталог
нормализованных таблиц).

## 9.3. Диагностика качества и корпоративные события (этап 6)

Модуль `equity_factor_study.validation` содержит набор проверок качества,
применяемых к нормализованной дневной таблице цен. Модуль
`equity_factor_study.pipelines.audit` оркеструет их и формирует отчёты.

### Проверки качества

| Проверка | Тип замечания | Смысл |
|---|---|---|
| Неположительная цена | `nonpositive_price` | Цена закрытия ≤ 0 |
| Аномально большой дневной скачок | `large_day_change` | Изменение > порога (0.5) |
| Длинный интервал без торгов | `trading_gap` | Календарный разрыв > порога (10 дней) |
| Расхождение объёма | `volume_discrepancy` | Сумма дневных `VALUE` против ожидаемого агрегата |
| Отсутствие цены в торговый день | `missing_price_on_trading_day` | Торговый день без цены (нет строки либо цена пуста) |

Каждое замечание сохраняется одной строкой с колонками `secid`, `date`,
`type`, `value`. Сводка качества (`quality_summary.csv`) содержит счётчики
замечаний по типам.

### Корпоративные события

Корпоративные события выявляются по данным о корпоративных действиях
(таблица-артефакт `data/interim/corporate_actions.csv` с колонками `secid`,
`date`, `event_type`), а не по величине скачка цены. Ряд **не исправляется**
единым порогом изменения цены: событие помечается отдельно, а доходности
считаются по исходным ценам. Даты, совпадающие с задокументированным
событием, исключаются из замечания `large_day_change`.

### Выход этапа

`audit` CLI-команда читает `data/interim/daily_prices.csv` и
`data/interim/corporate_actions.csv`, прогоняет проверки и пишет в
`data/reports/` файлы `findings.csv` (замечания),
`corporate_events.csv` (события) и `quality_summary.csv` (сводка).
