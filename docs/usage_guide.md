# Руководство по работе с инструментом

Практический справочник: как собрать данные, какие акции искать, что за
данные нужны, как построить панель и как её анализировать (графики и выводы
о наличии или отсутствии закономерностей).

Инструмент реализует протокол «Оценка вневыборочной полезности факторов в
моделях доходности российских акций». Итог — месячная панель
(`monthly_panel.csv`) и манифест (`dataset_manifest.json`), из которых
строится и оценивается модель доходности. Документ дополняет `protocol.md`
(строгие правила) и `data_dictionary.md` (схема данных).

---

## 1. Конвейер одним взглядом

```
configs/study.toml  ──►  все команды ниже читают его (правила отбора, период,
                         признаки, окно модели)

сбор исходных данных (сеть → data/raw, без изменений исходников):
    catalog      справочники инструментов / режимов торгов (MOEX ISS)
    universe     состав выборки → configs/universe.lock.toml (+исключения)

нормализация (локально → data/interim):
    prices       дневные цены выбранных бумаг  → data/interim/daily_prices.csv
    key-rate     общедоступный ряд ЦБ          → data/interim/key_rate.csv

диагностика (локально → data/reports):
    audit           проверки качества и корпоративные события
    collect-events  зафиксировать корпоративное событие (полуручной сбор)

модельная панель (локально → data/processed):
    panel        месячные наблюдения           → monthly_panel.csv + манифест

проверки качества пайплайна:
    acceptance   детерминизм, отсутствие утечки, отчёт приёмки

модельный слой (§6, поверх готовой панели):
    evaluate     OLS с полным набором + полезность факторов
    selection    отбор состава факторов, сравнение моделей A/B/C
    bootstrap    парный блочный бутстрэп разности MSE моделей B и C
    sensitivity  проверки устойчивости процедуры отбора
    report       сводный отчёт (markdown + графики)
```

**Порядок запуска** почти всегда одинаков: `catalog → universe → prices →
key-rate → audit → panel`. Далее — анализ панели (см. §6).

## 2. Что собирает команда и какие файлы создаёт

| Команда | Источник | Что получаем | Где лежит |
|---|---|---|---|
| `catalog` | MOEX ISS | справочники инструментов и режимов торгов | `data/raw` (выгрузка страниц) |
| `universe` | справочники | состав выборки + список исключений и причин | `configs/universe.lock.toml`, `configs/universe_exclusions.csv` |
| `prices` | MOEX HIV | дневные цены по каждой бумаге из замка | `data/interim/daily_prices.csv` |
| `key-rate` | ЦБ РФ (CBR) | дневной ряд ключевой ставки | `data/interim/key_rate.csv` |
| `audit` | панель/цены | замечания качества, корпоративные события | `data/reports/findings.csv`, `corporate_events.csv`, `quality_summary.csv` |
| `panel` | interim | месячная панель + манифест | `data/processed/monthly_panel.csv`, `dataset_manifest.json` |
| `acceptance` | синтетика | отчёт приёмки этапа 8 | `data/reports/acceptance_report.*` |
| `evaluate` | панель | OLS + полезность факторов | `data/reports/model_evaluation.json` |
| `selection` | панель | модели A/B/C, правило отбора | `data/reports/selection_report.json` |
| `bootstrap` | отчёт отбора | интервал разности MSE (C−B) | `data/reports/bootstrap_report.json` |
| `sensitivity` | панель | проверки устойчивости | `data/reports/sensitivity_report.json` |

Каталоги `data/raw`, `data/interim`, `data/processed`, `data/reports`
вынесены из-под контроля версий (как и `configs/universe.lock.toml`).
Пер-прогонные выгрузки идут в уникальный каталог прогона
`<raw-dir>/<timestamp>_<run_id>/<source>` — повторный запуск не перезаписывает
исходные файлы (защита от нарушения инварианта неизменности данных).

## 3. Какие акции искать (что считает `universe`)

**Не нужно искать акции вручную.** Состав выборки вычисляется `universe` по
правилу из `configs/study.toml` и фиксируется в `configs/universe.lock.toml`.
Работают фильтры:

* **Биржевой режим** — `selection_board = "TQBR"` (основной режим торгов,
  акции);
* **Тип бумаги** — `security_type = "common_share"` (обыкновенные акции);
  фильтр опирается на семантическую метку `common_share` → код ISS `"1"`,
  чтобы справочник не отсекал всех;
* **Оборот начального года** — `turnover_year = 2014`, сортировка по обороту
  по убыванию (`selection_rule = "turnover_2014_desc"`);
* **Целевой размер** — `target_size = 10`; это параметр, а не рекомендация:
  если после фильтров прошло меньше, выборка принимается в фактическом
  объёме (`allow_fewer = true`), а причина недобора фиксируется в файле
  исключений `configs/universe_exclusions.csv`.

**Что считать «подходящими» акциями:** те, что торгуются в режиме TQBR и
относятся к обыкновенным акциям, с наибольшим оборотом в базовом
(начальном) году. Дополнять выборку бумагами, не прошедшими фильтры, и
ослаблять фильтры ради достижения «десяти» — **запрещено** (это вернуло бы
ошибку выживших через иной механизм отбора).

**Правило ошибки выживших.** `require_survive_to_end = false` — отбор
опирается **только на данные базового (2014) года**, а не на «дожитие до
конца периода». Это исключает отбор бумаг, которые просто дожили до сегодня.
При изменении состава замка обязательна запись в журнале решений.

**Защита от перезаписи замка.** `universe` не перезаписывает существующий
`universe.lock.toml` автоматически: при повторном запуске без явного
подтверждения команда завершается ошибкой. Для осознанной пересборки
передайте `--force`.

**Ручная проверка состава.** После `universe` можно внести результат
проверки — исключение по причине **качества данных** (разрыв истории без
события, смена кода без непрерывности, почти полное отсутствие торгов,
расхождение типа бумаги):

    pi run universe --exclude GAZP:...   # через общий CLI
    equity-factor-study --config configs/study.toml review \
        --exclude GAZP data_gap_unexplained

Исключение по «ожидаемой доходности» или «непривычности» эмитента кодом
отклоняется — оно вернуло бы смещение отбора.

## 4. Какие данные нужны и что они означают

### 4.1. Дневные цены — `data/interim/daily_prices.csv`
Колонки: `secid, trade_date, close, value` (цена закрытия и оборот).
После `prices` цены нормализованы: выбран режим торгов `BOARDID`,
даты/числа приведены к канону, дубликаты по `(secid, trade_date)` удалены.

Это основа для `return_1m`, `momentum_prev_3m`, `volatility_3m` и целевой
доходности. **Никакой ручной чистки не требуется** — панель помечает
проблемы в `quality_flags`, а не домысливает цены.

### 4.2. Ключевая ставка — `data/interim/key_rate.csv`
Колонки: `date, rate` (в % годовых). Загружается из ЦБ РФ (`CBRClient`).
В панели:
* `key_rate_pct` — ставка, действующая на последний торговый день месяца;
* `key_rate_change_pp` — разность действующих значений смежных месяцев.

Соглашение едино во всём коде: применяется ставка, действующая на конец
месяца, изменение — по разности на конец смежных месяцев (проверяется TL-4).

### 4.3. Корпоративные события — `data/interim/corporate_actions.csv`
Колонки: `secid, date, event_type` (обязательные) и `coef, source,
retrieved_at` (опциональные сведения). Берутся из официального источника
(например, таблицы действий MOEX), **не** из скачка цены. Ряд не исправляется
порогом: событие помечается отдельно, а для сплита/консолидации (`split` с
`coef`) цены до даты события приводятся к единому масштабу **официальным
коэффициентом** при сборке панели (см. `data/reports/corporate_events.csv`).

Файл — **обязательный вход**: его отсутствие является ошибкой (шаг A1).
Пустая таблица (существующий файл без событий) допустима. Если машинный
маршрут недоступен, событие фиксируется полуручно командой:

```
python -m equity_factor_study collect-events \
    --secid VTBR --event-date 2024-07-15 --event-type split \
    --coef 4663.8 --source computed_from_moex_history --retrieved-at 2026-10-24
```

### 4.4. Период наблюдения (из `configs/study.toml`)
* `download_start = 2013-07-01` — раньше `observation_start` (нужны дневные
  доходности до первого месяца для волатильности);
* `observation_start = 2014-01-01`, `observation_end = 2026-09-30`;
* `development_target_end = 2020-12-31`, `evaluation_target_start = 2021-01-01`.

### 4.5. Месячная панель — `data/processed/monthly_panel.csv`
Одна строка на пару «инструмент-месяц`. Признаки и целевая переменная:
`return_1m`, `momentum_prev_3m`, `volatility_3m`, `key_rate_pct`,
`key_rate_change_pp`, `target_return_next_1m`. Пропуски допустимы только при
непустом `quality_flags`. Подробная схема — в `data_dictionary.md`.

## 6. Как анализировать собранные данные

Цель — оценить **вневыборочную полезность факторов**: предсказывают ли
признаки доходность следующего месяца на данных, которых не было при
обучении. Панель уже содержит всё необходимое; анализ делается поверх неё, а
не руками в сырых данных.

### 6.1. Три среза данных (обучение / разработка / оценка)
Разделение задано в конфигурации:
* **обучение** — окно 48 месяцев, сдвигается ежемесячно;
* **разработка** — целевые месяцы `2018-06..2020-12` (31 прогноз), расходуется
  на разогрев правил отбора и калибровку;
* **оценка** — целевые месяцы с `2021-01` (69 прогнозов) — честная
  вневыборочная проверка.

В первые прогнозы периода разработки (июнь 2018 — июнь 2019) разогревают
процедуру отбора состава и **не входят в метрики оценки**. Это зафиксировано
`warmup_from = "development"`.

### 6.2. Что строить и смотреть
* **Плотность данных**: сколько строк на инструмент-месяц, доли пропусков по
  `quality_flags`. Большие доли `stale_price_too_far_from_month_end` или
  `no_trading_days_in_month` — сигнал к пересмотру допуска по концу месяца.
* **Распределения**: `return_1m`, `momentum_prev_3m`, `volatility_3m` —
  гистограммы отдельно для разработки и оценки. Смещение распределений между
  срезами — признак нестационарности.
* **Корреляции**: признаки ↔ `target_return_next_1m`. Сильная корреляция
  признака с целевой **в обучении, но отсутствие в оценке** — типичный признак
  переобучения фактора.
* **Доходность по квинтилям**: сортировка наблюдений по каждому признаку,
  доходность следующего месяца в квинтилях. Вневыборочно полезный фактор даёт
  монотонный профиль в оценке. Монотонность только в обучении — ложная
  закономерность.
* **Целевая vs предсказание (post-model)**: после построения модели — график
  фактической и прогнозной доходности по месяцам, разбивка по срезам.
* **Робастность к ставке**: меняется ли вывод при `key_rate_pct` vs
  `key_rate_change_pp` как факторе (это проверка чувствительности,
  обязательная к отражению в отчёте).

### 6.3. Формат выводов
Для каждого фактора фиксируйте:
1. **Направление влияния** (знак связи в обучении);
2. **Устойчивость** (связь сохраняется ли вне выборки — во время оценки);
3. **Размер эффекта** (величина, а не только значимость);
4. **Вывод** — фактор полезен / не полезен / требует проверки.

Ключевой принцип: закономерность признаётся, только если она **выглядит
одинаково в обучении и в оценке**. Различие между срезами — это не «шум», а
главный предмет исследования.

### 6.4. Чего делать НЕ надо
* Не исправлять цены «на глаз» и не убирать события дробления порогом —
  панель сама помечает проблемы.
* Не менять состав выборки и не ослаблять фильтры ради полноты.
* Не использовать `key_rate_pct` из будущего месяца для настоящего (утечка,
  ловится А.4/TL-4).
* Не перезаписывать `data/raw` — это исходник; повторный прогон создаёт новый
  каталог.

### 6.5. Отбор состава факторов (модель C) и бутстрэп
Команды `selection` и `bootstrap` реализуют методику из документа
«Оценка вневыборочной полезности факторов» (разделы 3.2–3.5).

**Три модели:**
* **A** — историческое среднее: прогноз = средняя реализованная доходность за
  то же обучающее окно (без факторов). Минимальный ориентир.
* **B** — OLS по каждой акции отдельно, полный набор из пяти признаков.
* **C** — та же регрессия по каждой акции, но состав факторов пересматривается
  раз в квартал по ошибкам предшествующих прогнозов.

**Восемь составов** образуются из трёх групп признаков (таблица 2): ценовая
динамика `{return_1m, momentum_prev_3m}`, риск `{volatility_3m}`, макро
`{key_rate_pct, key_rate_change_pp}`. Пустой состав соответствует модели A.

**Правило отбора (раздел 3.3):** на каждой дате квартального пересмотра для
каждого состава вычисляется средняя месячная MSE за 12 предшествующих месяцев;
выбирается состав с минимумом. При равенстве предпочтение отдаётся более
простому составу (меньше признаков, `tie_break = "fewest_features"`). Единый
состав применяется ко всем акциям (`pooled_across_securities`). Первый
пересмотр — 1 июля 2019 после 13 прогнозов разогрева период разработки
(пункт Б.4).

**Бутстрэп (раздел 3.5):** парный блочный бутстрэп по месячному ряду разностей
MSE (C−B). Перекрывающиеся блоки длины `block_months=6`, 5000 повторов,
фиксированное зерно `seed`. По эмпирическому распределению средних строятся
границы 95% интервала. Интерпретация: интервал целиком выше нуля — процедура
обновления состава даёт систематический выигрыш; целиком ниже нуля —
ухудшает; содержит ноль — данных недостаточно.

Выводы по моделям A/B/C и бутстрэпу — содержательная часть исследования
(этап §6), выполняемая после приёмки панели. Команда `report` собирает всё в
единый сводный отчёт (`summary_report.md`) с таблицами метрик, интерпретацией
по трём сценариям и тремя графиками:

* `errors_B_C.png` — месячная MSE моделей B и C на периоде оценки;
* `rebalance_history.png` — число признаков выбранного состава по датам
  пересмотра;
* `bootstrap_distribution.png` — распределение бутстрэп-средних разности
  C−B с границами 95% интервала и линией нуля.

## 7. Частые вопросы

**Нужно ли что-то руками искать в MOEX?** Нет. `catalog` и `universe`
собирают справочники и состав автоматически. Вручную только задаётся правило
в `configs/study.toml`.

**Можно ли менять период наблюдения?** Да, но только согласованно с
контрольными датами (пункт Б.6): сдвиг `observation_start` сдвигает `s₀` и
первый целевой месяц. `panel` и `acceptance` проверят согласованность.

**Что показывают `quality_flags`?** Причины пропусков и замечаний:
`no_trading_days_in_month`, `missing_close_price`,
`stale_price_too_far_from_month_end`, `no_previous_price` и др. Это не ошибки
пайплайна, а честная фиксация качества данных.

**Как проверить, что пайплайн не искажает данные?** Команда `acceptance`
прогоняет проверки детерминизма (TD-1..TD-7) и отсутствия утечки (А.4,
TL-1..TL-9). Отчёт в `data/reports/acceptance_report.md`; этап принят только
при отсутствии расхождений.

**Где смотреть корпоративные события?** `data/reports/corporate_events.csv`
и `data/reports/findings.csv` — замечания и события, помеченные отдельно от
ряда цен.

## 9. Модельный слой (после приёмки панели)

Команда `evaluate` обучает модель на построенной панели и оценивает
полезность факторов. Реализовано в `src/equity_factor_study/model/` и
соблюдает инварианты протокола.

### Что делает `evaluate`

```bash
python -m equity_factor_study evaluate
```

Читает `data/processed/monthly_panel.csv`, строит матрицу наблюдений по
единой маске доступности (инвариант 5), обучает скользящую линейную модель
(OLS) по правилу пункта Б.6 и пишет отчёт
`data/reports/model_evaluation.json`.

### Инварианты, которые соблюдает модельный слой

* **Маска доступности (инвариант 5)** — множество пригодных наблюдений
  строится один раз; модель с сокращённым набором признаков использует те же
  строки, не получая доступ к более широкому набору.
* **Нормировка только на обучении (инвариант 6)** — среднее и разброс
  признаков считаются в пределах обучающего окна и применяются к оценке без
  пересчёта.
* **Отсутствие утечки (инвариант 1)** — прогноз на целевой месяц `t+1`
  использует только пары «признаки месяца s — доходность s+1» для s из
  `[t−W, t−1]`.

### Скользящее переобучение

Первое обучение возможно в месяце `s₀ + W + 1` (для штатных значений —
июнь 2018). Модель переобучается ежемесячно (`refit_frequency = "monthly"`),
окно — `training_window_months = 48` месяцев. Прогноз на каждый целевой
месяц формируется на наблюдениях окна; маска наблюдений не расширяется
сокращённым набором признаков.

### Что даёт отчёт `model_evaluation.json`

* `forecast_count` — число спрогнозированных целевых месяцев;
* `mse` / `mae` — метрики точности (агрегация `securities_then_months`);
* `factor_usefulness` — для каждого фактора прирост ошибки (в %) при его
  удалении на срезе оценки. Положительный прирост (“удалили — стало хуже”)
  означает, что фактор полезен вне выборки; отрицательный — не улучшает или
  вредит.

### Как читать результат полезности фактора

* **Устойчивая полезность** — фактор при удалении заметно ухудшает ошибку
  оценки (положительный прирост) и это повторяется при замене окна
  (`window_sensitivity`).
* **Вредный фактор** — удаление улучшает ошибку (отрицательный прирост).
* **Нейтральный** — прирост близок к нулю; фактор не несёт вневыборочной
  информации.

Интерпретация: полезным считается фактор только тогда, когда его вклад
сохраняется вне выборки. Если фактор улучшает ошибку лишь в обучении, а в
оценке вредит или нейтрален — это переобучение, и фактор для исследования
не пригоден.

### Что ещё не реализовано (следующие шаги)

* **Отбор состава факторов** (`selection`) — выбор подмножества факторов по
  критерию `aggregation = "securities_then_months"` и разогрев из
  `warmup_from = "development"`.
* **Бутстрэп** (`bootstrap`) — доверительные интервалы метрик
  (`paired_block`, `block_months = 6`, `replicates = 5000`).
* **Отчёт по инвестиционным выводам** — ним лучше не смешивать с оценкой
  полезности фактора: это отдельная содержательная задача.

Предлагаемый следующий шаг: отбор состава факторов и бутстрэп-интервалы,
затем графики распределений признаков и профилей доходности по квинтилям
(см. §6.2) на реальной панели.
